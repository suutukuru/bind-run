## ADR-001 エンジンと言語

- 日付: 2026-10-19 / 状態: 採用（オーナー指定の第一候補）
- 背景: スマホ（iOS/Android）向け 2D ゲーム。Windows で開発。
- 選択肢: (1) Godot 4 + GDScript (2) Godot 4 + C# (3) Unity
- 採用: (1) Godot 4.7.x（2026-10-19 時点の最新安定版 4.7.2）+ GDScript
- 理由: オーナー指定。2D に強く軽量。GDScript は記述量が少なく学習しやすい。
- 不採用理由: C# はモバイル書き出しの成熟度と導入の手間がかかる。Unity は指定外。
- トレードオフ: GDScript は大量の敵の処理で C# より遅い場合がある → 計測してから対処（R-03）。
- 将来への影響: マイナーバージョン（4.7 → 4.8）を上げるときは changelog に記録し、テストを再実行する。

## ADR-002 接続点（ハブ）のモデル ★最重要

- 日付: 2026-10-19 / 状態: 採用（仮決定）。Phase 2 で再評価
- 解決したい問題: 「接続点は固定されていないのに、2 人はどう接続されるのか」。ハブの位置を誰が決めるかを定義しないと、最大長・攻撃判定・描画がすべて決められない。

### 重要な気づき

紐が **2 本だけ** で、ハブに重さ（慣性）がない場合、両側から引かれたハブは必ず **A と B を結ぶ線分の上** に来る（両側の張力がつり合う位置が線分上にしかないため）。つまり 2 人の場合、「ハブ経由の 2 本の紐」と「A〜B を直結する 1 本の紐」は見た目以外ほぼ同じになる。ハブが意味を持つのは次の 2 つの場合。
- ハブに慣性を持たせる（遅れてついてくる → 紐が「く」の字に曲がる、しなる）
- 3 人以上がつながる（将来のマルチプレイ。Y 字・星形になる）

### 選択肢

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A. 計算ハブ（重心） | ハブ = 全キャラ位置の平均。各キャラはハブから半径 R 以内 | 実装が最小。表示と無関係にロジックが決まる。3〜4 人にそのまま拡張できる | 2 人では紐が常に一直線（しなりがない） |
| B. 慣性ハブ | ハブが質点として位置と速度を持ち、紐に引かれて遅れて動く | 紐がしなり、「振り回す」攻撃の余地がある | 調整項目が増える。挙動が不安定になりやすい |
| C. ハブなし直結 | A〜B を 1 本の紐で直結。最大長 L | 最も単純 | 「共通の接続点」という仕様から外れ、3 人以上に拡張しにくい |

### 採用

**案 A（計算ハブ）をプロトタイプの基準にする。** ハブの計算を `RopeModel.hub_position()` 1 か所に閉じ込め、Phase 2 で案 B を同じ場所の差し替えとして試作する。

- 2 人のとき: ハブ = A と B の中点。各キャラ〜ハブの最大長 R = L/2 なので、A〜B 間の最大距離は L。
- 理由: 仕様（共通接続点・表示とロジックの分離・将来の多人数化）を満たす最小の案。
- 変更可能性: 高い。ハブの計算は 1 関数に閉じているため、B 案への差し替えは RopeModel と Rope ノードの中だけで済む。

## ADR-003 紐の拘束方式（どう「制限」するか）

- 日付: 2026-10-19 / 状態: 採用（段階的）
- 選択肢:

| 案 | 内容 | 実装コスト | 安定性 | 操作感 | 調整のしやすさ |
|---|---|---|---|---|---|
| 1. 距離制限（位置の補正） | 移動後、最大長を超えた分だけ位置を戻す | 小 | 非常に高い | 硬い壁のような感触 | 長さ 1 個のみ |
| 2. ばね（フックの法則） | 伸びに比例して引き戻す速度/力を加える | 中 | 強すぎると振動 | ゴムらしい | 強さ・減衰 |
| 3. 物理ボディ + ジョイント | RigidBody2D と DampedSpringJoint2D 等 | 中〜大 | 操作キャラと相性が悪い | 物理任せ | 多い・予測しにくい |

- 採用: **1 を土台にし、Phase 2 で 2 を「たるみ長〜最大長」の区間だけに重ねる**ハイブリッド。
  - たるみ区間（0〜自然長）: 力なし
  - 弾性区間（自然長〜最大長）: 伸びに比例して引き戻す
  - 限界（最大長）: 位置補正で絶対に超えない
- 不採用理由（3）: プレイヤーの入力で直接動かすキャラクターを物理ボディにすると、操作が「滑る・重い」感じになりやすく、調整が難しい。紐の目的は物理の再現ではなく、操作感の設計である。
- 未決定（U-02）: 限界時に「外へ動いた側を止める」か「相方を引きずる」か。Phase 1 は計算が最も単純な「両者を等しくハブへ戻す（= 相方を半分引きずる）」で実装し、Phase 2 で比較する。

## ADR-004 キャラクターのノード種別

- 日付: 2026-10-19 / 状態: 採用
- 選択肢: CharacterBody2D / RigidBody2D / Area2D + 自前移動
- 採用: **CharacterBody2D**（コードで速度を決め、`move_and_slide()` で動かす種類の物理ボディ）
- 理由: 入力に素直に反応し、将来の壁や障害物との衝突も Godot に任せられる。
- A と B はお互いに衝突しない（コリジョンレイヤーで除外）。

## ADR-005 入力とキャラクターの分離

- 日付: 2026-10-19 / 状態: 採用
- 問題: PC キーボード、ゲームパッド、タッチスティック、将来はネットワークや AI からもキャラを動かしたい。
- 採用: キャラクターは「移動したい方向（`move_intent: Vector2`）」だけを受け取る。誰がそれを設定するかは知らない。入力担当ノード（`KeyboardMoveInput`、後で `TouchStickInput`）が毎フレーム intent を書き込む。
- 不採用: キャラ内で `Input.is_action_pressed()` を直接読む → 入力方式の追加のたびにキャラを書き換えることになる。
- トレードオフ: ノードが 1 段増える。代わりに、テストではキャラに intent を直接与えて動かせる。

## ADR-006 テスト方式

- 日付: 2026-10-19 / 状態: 採用（仮決定）
- 選択肢: (1) 自作の最小テストランナー (2) GUT アドオン (3) GdUnit4 アドオン
- 採用: (1)。ロジックをノードから切り離した純粋なクラス（例: `RopeModel`）に置き、`godot --headless --script res://tests/run_tests.gd` で実行する。
- 理由: 外部依存ゼロ。最初のテスト対象は数学関数が中心で、高機能なフレームワークはまだ不要。
- 将来: テストが増えてシーン単位のテストが必要になったら、4.7 対応を確認したうえで GUT / GdUnit4 を再検討する。

## ADR-010 レンダラー（描画方式）

- 日付: 2026-10-19 / 状態: 採用（仮決定）
- 問題: Godot 4 のレンダラー（画面に絵を描く仕組み）は Forward+ / Mobile / Compatibility から選ぶ。後から変えられるが、見た目の機能差が出る。
- 選択肢:

| 案 | 特徴 | このゲームでの評価 |
|---|---|---|
| Forward+ | 高機能。PC 向け | 2D 中心のため不要。スマホには重い |
| Mobile | スマホ向けの 3D 寄り | 2D では利点が小さい。Web 版では使えない（※） |
| Compatibility | 最も軽く互換性が高い（OpenGL 系） | 2D には十分。Web 版・古い端末でも動く |

- 採用: **Compatibility**（`gl_compatibility`）
- 理由: 2D ゲームなので高機能な描画は不要。Web 版でスマホのブラウザ確認（TASK-016）をする計画で、Godot 4 の Web 書き出しは Compatibility のみ対応と認識している。
- 確認済み: Godot 4 の Web 書き出しは WebGL 2.0 のみ対応で、Compatibility が必要（公式ドキュメント 4.2 版で確認。4.7 版は未確認）。
- 変更可能性: 高い。プロジェクト設定 1 行（`renderer/rendering_method`）。ただし 2D の光・影・一部シェーダーの見た目が変わる可能性がある。

## ADR-011 クラス自身の enum を変数の型にしない

- 日付: 2026-10-19 / 状態: 採用
- 問題: `TouchMoveInput` の `@export var side: Side = Side.LEFT`（`Side` は同じクラスの enum）が、**ゲームを直接起動したときだけ**「Cannot assign a value of type TouchMoveInput.Side as Side」で読み込めなかった。単体テストは読み込み順が違うため通っていた。公開中の版でタッチ入力が動いていなかった可能性が高い。
- 選択肢: (1) enum を別ファイルに分ける (2) int の定数 + `@export_enum` (3) 型指定を外す
- 採用: **(2)**。最も単純で、エディタのインスペクタでも選択肢として出る。
- 教訓: 単体テストが通っても、ゲームの起動経路でしか起きない不具合がある。CI に「ゲームシーンを実際に起動するスモーク実行」を追加した。

## ADR-012 画面の向きに依らない見た目の大きさ

- 日付: 2026-10-19 / 状態: 採用（仮決定。U-01 の決定後に見直す）
- 問題: 画面設定が `canvas_items` + `expand` のため、縦持ちでは表示範囲が縦に大きく広がり、半径 16px のキャラが数 px の点になった（オーナー報告「画面でてないかも」）。
- 選択肢: (A) 画面を横持ち専用にする (B) カメラのズームを短辺に合わせて補正する (C) ストレッチを `keep_height` などに変える
- 採用: **(B)** と、UI の大きさを短辺の割合（`UiScale`）にすること。向きが未決定（U-01）でも縦横どちらで開いても遊べる。
- トレードオフ: 縦持ちのとき、縦方向にはより広いワールドが映る（上下の敵が見えやすい）。向きを決めれば、その向けに見える範囲を調整できる。

## ADR-013 ゲーム内の文字は当面英語のみ

## ADR-014 戦闘の判定は物理エンジンを使わず距離で行う

- 日付: 2026-10-19 / 状態: 採用
- 問題: 敵が 150 体以上になっても軽く、武器・弾・紐攻撃・経験値の判定を同じ方式で扱いたい。
- 選択肢: (1) `Area2D` / 物理ボディの衝突 (2) 距離の計算（円と円、点と線分）
- 採用: **(2)**。紐は毎フレーム形が変わる線分なので、図形を作り直すより計算式 1 つのほうが単純でテストしやすい（ADR-008 の推奨を採用）。敵は `Node2D` で、押し合いはしない。
- トレードオフ: 敵同士が重なって一団になる。見づらければ Phase 7 で簡易な分離を検討。壁や障害物を入れるときは判定を足す必要がある。
- 計測: CI で敵 150 体 × 120 フレームの処理時間を記録（描画なし）。実機の FPS は未確認。

## ADR-015 強化はデータ（パス + プロパティ + 増減量）で表す

- 日付: 2026-10-19 / 状態: 採用
- 問題: 強化の種類を増やすたびにコードを書きたくない。武器・キャラ・紐・HP・経験値の吸い寄せなど、対象がばらばら。
- 選択肢: (1) 強化ごとにスクリプトを書く (2) 「対象ノードのパス + プロパティのパス + 加算/乗算」の汎用定義にする
- 採用: **(2)**（`UpgradeDef`）。`.tres` を増やして `UpgradePool` に足すだけで強化を増やせる。入れ子のプロパティ（`config:attack_damage`）も `set_indexed` で書ける。
- トレードオフ: 「条件つきの効果」や「新しい挙動を足す」強化は表せない。必要になったらその強化だけスクリプトにする（過剰に汎用化しない）。
