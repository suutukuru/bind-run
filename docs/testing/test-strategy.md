# テスト戦略

- 版: 0.1 / 2026-10-19

## 1. 目的

1. ルールや計算が仕様どおりか（**正しさ**）を機械的に保証する。
2. 実際に触って **遊びやすいか・面白いか** を人が評価する。

ゲームは「コードは正しいのに遊ぶとつまらない／操作しにくい」ことがよくあるため、2 は 1 と同じくらい重要。

## 2. テストの種類

| 種類 | 対象 | 方法 | 実行者 | ID 帯 |
|---|---|---|---|---|
| 単体テスト | 純粋な計算（RopeModel、ダメージ計算、XP 計算） | 自作ランナーを headless 実行（ADR-006） | Claude（環境があれば）/ オーナー | TC-001〜 |
| 機能テスト | 1 つの機能が画面上で期待どおり動くか | 手順書に沿った手動操作 | オーナー | TC-101〜 |
| 結合テスト | 複数機能の組み合わせ（紐攻撃で倒した敵が XP を落とす等） | 手動。可能な部分はシーンを使う自動テストへ | オーナー | TC-201〜 |
| 手動プレイテスト | 面白さの仮説 H-01〜06 | 数分遊んで感想と数値を記録 | オーナー | PT-001〜 |
| パフォーマンステスト | FPS と敵数 | デバッグ表示で計測。端末ごとに記録 | オーナー | PF-001〜 |
| プラットフォーム別テスト | Windows / Android / iOS で起動・操作・表示 | 実機 | オーナー | PL-001〜 |

## 3. 自動テストの実行方法

```
godot --headless --path <プロジェクトのフォルダ> --script res://tests/run_tests.gd
```

- **headless**: 画面を出さずに実行するモード。
- 終了コード 0 = 全件成功、1 = 失敗あり。
- 現状: Claude のクラウド環境には Godot がない（R-08）。オーナーが Windows で実行し、出力を貼り付けてもらう。

## 4. テストしやすくするための設計ルール

- 計算はノードから切り出して静的関数にする（例: `RopeModel`）。
- キャラは `move_intent` を直接与えれば動くため、入力デバイスなしで挙動を確かめられる（ADR-005）。
- 乱数を使う処理（敵の出現位置など）は、シード（乱数の初期値）を指定できるようにし、結果を再現できるようにする。

## 5. 不具合の記録方法

test-results.md の「不具合」表に記録する。

| 項目 | 内容 |
|---|---|
| BUG-ID | BUG-001 から連番 |
| 現象 | 何が起きたか |
| 再現手順 | 操作の手順 |
| 期待結果 | どうなるべきか |
| 環境 | OS / Godot バージョン / コミット |
| 重要度 | P0〜P3 |
| 状態 | Open / Fixed / Verified |

修正後は、同じ手順の再テスト結果を必ず書く。

## 6. 記録のルール

- 実行していないテストを「実施済み」にしない。
- 「ファイルを作った」ことと「動作を確認した」ことを区別する。
