# 学習ログ

## 2026-10-19 Phase 0: 実装前に「仕組みのモデル」を決める

### 学んだ概念 1: 仕様の曖昧さは「状態を誰が持つか」で解消する

- **必要な理由**: 「共通の接続点」と言っても、その位置を誰がどう決めるかを決めないと、最大長・当たり判定・描画を設計できない。
- **今回の例**: 接続点（ハブ）を「独立した物体」ではなく「2 人の位置から毎フレーム計算される値（重心）」と定義した（ADR-002）。
- **別の方法**: ハブ自体に位置と速度を持たせ、紐に引かれて遅れて動く質点にする（慣性ハブ）。
- **採用理由**: 最小の実装で仕様を満たし、3〜4 人にもそのまま拡張できる。表示を消してもロジックは同じ値を使う。
- **得られた知見**: 重さのないハブを 2 本の紐で引くと、ハブは必ず A〜B の線分上に来る。つまり 2 人では「ハブ経由」と「直結」はほぼ同じ。ハブが本当に意味を持つのは、慣性を持たせたときか 3 人以上のとき。こうした「当たり前のようで当たり前でない」性質を、実装前に紙の上で確かめておくと手戻りが減る。

### 学んだ概念 2: 物理を「再現」するのではなく「設計」する

- ゲームの物理は現実の正確さより **操作して気持ちいいか** が優先される。
- 紐を本物の物理（RigidBody + ジョイント）で作ると、プレイヤーが動かすキャラが滑る・重い・予測しにくい挙動になりやすい。
- そこで「位置を直接補正する（絶対に超えない）」＋「一部の区間だけばねの力」という作られた物理を採用した（ADR-003）。

### 学んだ概念 3: ゲームループと処理順

- 毎フレーム「入力 → 移動 → 拘束 → 描画」の順に処理する。順番を間違えると、紐が一瞬伸びすぎて見えるなどの不具合になる。Godot では `process_priority` で順番を指定する。

### 次に理解するとよい内容

- `Vector2` の基本操作（長さ、正規化、内積）。Phase 1 の拘束計算で使う。
- Godot のシーンとノードの木構造、`@export` によるインスペクタ編集。
- `_process` と `_physics_process` の違い。

## 2026-10-19 Phase 1 前半: テストを書いて初めて分かったこと

### 学んだ概念 1: 純粋な計算を切り出すと、テストが速く簡単になる
- 紐の計算（`RopeModel`）はノードを一切使わない静的関数にした。13 件のテストが一度で通り、ノードを使う部分で起きた不具合（下記）とは無関係だった。
- 別の方法: 計算をノードの `_physics_process` の中に直接書く。動かすたびに画面を出す必要があり、確認が遅く、数値例（`A=(0,0), B=(400,0)` → `(40,0), (360,0)`）の検証もしにくい。

### 学んだ概念 2: シーンの「準備」のタイミング（`_ready`）
- ノードの `_ready()` は「木に入り、準備が済んだ」ときに呼ばれる。`SceneTree._initialize()` の時点ではルートが未準備で、そこへ追加したノードの `_ready()` は呼ばれなかった。1 フレーム待てば呼ばれる。
- ゲーム本体でも同じ考え方が大事: ノード同士の参照は、`_ready()` の中で解決するのが安全。

### 学んだ概念 3: ノード参照は NodePath で持つほうが確実
- `@export var target: Character`（型付きのノード参照）は、スクリプトで定義した独自クラスの場合、シーンファイルから解決されなかった。
- `@export var target_path: NodePath` を受け取り、`_ready()` で `get_node_or_null()` する方式は確実に動いた（Rope も同じ）。

### 学んだ概念 4: テストが失敗したら、コードとテストの両方を疑う
- 今回の 3 件の不具合のうち、2 件はテストの前提（テスト環境）の問題、1 件は本体の参照方式の問題だった。ログを読んで原因を切り分けてから直した。
- 自動テストが「読み込めないテスト」も失敗として数える設計のおかげで、構文エラーを見逃さずに済んだ。

### 次に理解するとよい内容

- `Camera2D` の追従（TASK-012）
- タッチ入力（`InputEventScreenTouch` / `InputEventScreenDrag`、TASK-015）

## 2026-10-19 Phase 2〜5: 作ったものを「実際に動かして」確かめる

### 学んだ概念 1: 単体テストが通っても、ゲームの起動経路でしか起きない不具合がある
- `TouchMoveInput` は単体テストでは読み込めたのに、ゲームを直接起動すると構文エラーで読み込めなかった（クラス自身の enum を型にする書き方が、読み込み順で失敗）。
- 対策は「実際に起動する」テストを CI に足すこと（スモーク実行）。単体テスト・統合テスト・起動の確認は、それぞれ別の種類の不具合を捕まえる。
- 別の方法: 手で毎回遊んで確かめる。PC がない今の環境では現実的でなく、見落としも出る。

### 学んだ概念 2: 画面サイズに依存しない見た目（ストレッチとカメラのズーム）
- 画面設定の `expand` は「少なくとも基準サイズが映る」ようにする。縦持ちでは縦方向が大きく広がり、ワールドの 1px が画面で小さくなる。
- 解決は「画面の短辺に映すワールドの長さを一定にする」: ズーム = 短辺 ÷ 映したい長さ。UI の大きさも同じく短辺の割合（`UiScale`）で決める。スマホは機種ごとに縦横比が違うので、この考え方が基本になる。

### 学んだ概念 3: データ駆動（Resource）で「増やしやすい」作りにする
- 強化 13 種は、コードを書かずに `.tres` を増やすだけで追加できる（対象ノードのパスとプロパティのパス、増減量だけを持つ）。バランス調整もファイルの数値を変えるだけ。
- 限界: 条件つきの効果や新しい挙動は表せない。そのときだけスクリプトにする（過剰に汎用化しない）。

### 学んだ概念 4: 物理エンジンを使わない当たり判定
- 敵・弾・紐・オーブの判定をすべて「距離の計算」にした（円と円、点と線分）。数が増えても軽く、テストしやすい。
- 壁や障害物が必要になったら、そこだけ物理エンジンを足す。

### 学んだ概念 5: 状態を持つ場所を分ける
- ゲームのルール（HP・時間・レベル）は `RunState` が持ち、画面は信号（signal）を受けて表示するだけ。メニューの出し方は `Main` が決める。ルールを画面から分けておくと、ボットが画面なしで最後までプレイするテストが書けた。
